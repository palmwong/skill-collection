# Skill 设计实战指南

> 原文：https://zhuanlan.zhihu.com/p/2066536287952286744  
> 整理日期：2026-07-30  
> 本文记录 Skill 的本质、常见误区、设计方法和验收标准。

## 核心观点

**Skill 不是提示词的加长版。Skill 是把一套重复工作，沉淀成一个能被反复调用的工作流。**

提示词解决的是一次任务，Skill 解决的是一类反复出现的任务。

## 一、Skill 到底是什么

一个 Skill 本质上就是一个文件夹，通常包含：

| 文件/目录 | 作用 |
|---|---|
| `SKILL.md` | 主说明书：是什么、什么时候用、怎么做 |
| `references/` | 长资料、规则、模板、案例 |
| `scripts/` | 脚本：校验、转换、提取、格式化等稳定动作 |
| 其他辅助文件 | 示例、素材、配置 |

核心优势是**分层加载**：AI 不会一开始就背下所有内容，只有任务相关时才会读取 SKILL.md，用到资料时才打开 references，需要执行固定动作时才调用 scripts。

## 二、为什么很多人会把 Skill 写废

1. **触发不清楚**：没写清"什么情况下该用它"
2. **主文件太胖**：所有背景、规则、示例都堆进 SKILL.md
3. **把该交给脚本的事硬写成文字**：格式检查、文本清洗、字段提取、批量重命名、结构转换等更适合脚本

设计原则：**主文件只负责决策和流程，长资料放 references，稳定动作放 scripts。**

## 三、不是所有任务都值得做成 Skill

真正适合做成 Skill 的任务有三个特征：

- 高频重复
- 流程相对固定
- 某些步骤可以脚本化或校验

判断法：以下 4 个问题中有 3 个答案是"是"，就值得做。

- 这件事会反复发生吗？
- 它的输入和输出相对稳定吗？
- 它中间有固定步骤或判断标准吗？
- 如果换一个新对话，你还得重新解释一遍吗？

以下情况不适合做：一次性任务、一句话能说清、完全依赖临场发挥、只有一段顺手提示词。

## 四、先做工作流卡片，再建文件夹

不要先写格式。先填这 6 行：

```
工作流名称：
什么时候启动：
用户通常会提供什么：
执行步骤：
最终输出是什么：
什么结果算合格：
信息不足时怎么办：
```

如果这张卡片写不完整，说明流程还没理顺，先不要急着做 Skill。

### 示例：voice-notes-to-article

```
工作流名称：voice-notes-to-article

什么时候启动：
用户提到"语音整理""口播转文章""直播内容转稿""录音变提纲"时

用户通常会提供什么：
语音转录文本、主题、目标读者、想保留的观点

执行步骤：
1. 清理转录里的口头禅、重复句和明显错字
2. 提取核心观点和可用例子
3. 按主题重组结构，而不是按原始说话顺序照抄
4. 标记缺失的事实、数据或案例
5. 输出成一篇可继续扩写的文章草稿

最终输出是什么：
标题建议 + 文章结构 + 草稿正文 + 待补充信息清单

什么结果算合格：
保留原意，不编造事实，结构清楚，能继续写，不像纯转录稿

信息不足时怎么办：
先标注"待补充"，最多提出 3 个关键问题，不要猜
```

## 五、description 决定触发效果

AI 通常先看 Skill 的名字和描述，再判断是否相关。好的 description 必须同时回答：

- 这个 Skill 是干什么的
- 什么场景下应该触发它

差示例：

```yaml
description: 帮助整理文章
```

好示例：

```yaml
description: 将语音转录、直播口播或零散表达整理成结构清楚的文章草稿。用户提到语音整理、口播转文章、录音转提纲、直播内容成稿时使用。
```

## 六、最小 Skill 结构

第一版不用复杂，最小结构即可：

```
voice-notes-to-article/
├── SKILL.md
├── references/
│   └── article-template.md
└── scripts/
    └── clean_transcript.py
```

如果没有脚本或长资料，先只有 `SKILL.md` 也可以。

## 七、SKILL.md 的写法

写成操作手册，不是百科。示例结构：

```markdown
---
name: voice-notes-to-article
description: 将语音转录、直播口播或零散表达整理成结构清楚的文章草稿。用户提到语音整理、口播转文章、录音转提纲、直播内容成稿时使用。
---

# Voice Notes To Article

## Instructions

1. 先清理转录文本中的口头禅、重复和明显错字。
2. 提取核心观点、案例和情绪线索。
3. 按主题重组结构，不按原始说话顺序硬排。
4. 缺少事实、数据或人名时，标记为"待补充"，不要猜测。
5. 输出标题建议、文章结构、正文草稿和待补充清单。

## Output Format

- 标题建议 3 个
- 文章结构
- 草稿正文
- 待补充信息

## Quality Bar

- 保留原意，不要改写成立场相反的内容
- 不编造事实
- 结构要能继续扩写
- 正文读起来像文章，不像逐字转录
```

关键点：

- 正文写"动作"，不写空话
- 把容易出错的地方写死
- 主文件保持克制，资料堆该拆去 references

## 八、scripts 的价值

凡是"说很多次也还是机械"的动作，优先考虑写成脚本：

- 清理转录里的口头禅
- 校验输出结构是否完整
- 从文本里提取标题、时间、标签
- 转换格式
- 统一命名
- 批量生成模板

脚本执行稳定，且不需要把全部逻辑塞进上下文。

## 九、Skill 与 MCP 的区别

| | Skill | MCP |
|---|---|---|
| 职责 | 怎么做事（流程层） | 怎么连工具（接口层） |
| 说明 | 什么时候接、按什么顺序做、做到什么算合格 | 如何访问浏览器、数据库、日历、文档、邮件等外部能力 |

两者不是替代关系，而是左右手。一个 Skill 可以内部调用 MCP 工具。

## 十、Skill 的三种测试

一个 Skill 要稳定，至少过这三关：

1. **显式调用测试**：`请使用 $voice-notes-to-article 整理下面这段口播转录。`
2. **自然表达测试**：`帮我把这段直播内容整理成一篇能继续写的文章。`
3. **边界情况测试**：`我只有一段很乱的转录，很多信息都没讲全，你先帮我理理。`

测试后的问题定位：

| 问题 | 修改方向 |
|---|---|
| 没触发 | 改 description |
| 顺序总乱 | 改 Instructions |
| 老在瞎猜 | 加异常处理规则 |
| 主文件越来越肿 | 拆到 references |
| 机械动作老飘 | 放进 scripts |

## 十一、发布到 GitHub

本地跑通后，建议放到 GitHub，变成可版本化、可迭代、可同步、可分享的资产。

好处：

- 有备份
- 能看修改历史
- 多设备同步
- 可分享给团队或朋友

发布前检查：

- 没有 API Key
- 没有 Token
- 没有客户资料
- 没有内部规则
- 没有不该公开的案例

不确定就先放私有仓库。

## 十二、第一次做 Skill 最容易踩的 5 个坑

1. 把聊天记录原样塞进 SKILL.md
2. 一上来就做"大而全"的万能助手
3. 只有步骤，没有"什么算完成"
4. 验证通过就以为真的能用
5. 把该拆开的东西全堆进主文件

## 十三、给新手的最佳启动建议

不要先建目录、研究格式、想做多高级。先翻最近一个月的 AI 聊天记录，找出已经解释过两次以上的任务，然后把这 6 行填出来：

```
什么时候启动
用户会提供什么
执行步骤
最终输出什么
什么结果算合格
信息不足时怎么办
```

Skill 真正解决的是：把"我每次都得重新解释"，变成"它以后知道该怎么接这类活"。
