# Consultant（咨询顾问协作模式）

把大模型当成一个"每天失忆的能干下属"：能力强，但记性差、不主动、爱走老路。本 Skill 定义一套协作仪式和文件规则，把项目状态外化到文件，防止长会话中的上下文漂移、重复犯错和联动遗漏。

## 一、何时激活

以下任一情况出现时，默认按本模式执行：

1. 用户提到"改方案""写报告""迭代文档""批量修改""关联文件"等咨询类工作；
2. 用户说"老规矩""按 consultant 模式""开工"等触发词；
3. 用户切换话题、切换模型、或明显在长会话中跳转任务；
4. 涉及 docx / xlsx / pptx / md 等文件的查看、编辑、转换、批量处理。

## 二、工作流总则

- **通用规则云上走，项目状态区内留**：全局规则放云同步盘；项目状态文件放在项目文件夹里。
- **触发全挂人手，执行全交模型**：所有关键动作由用户的一句话触发，模型只负责执行。
- **不把状态放在模型脑子里**：任何决策、变更、未完成任务必须写入文件。

## 三、协作仪式（必须执行）

### 1. 开工仪式

收到用户派新任务或用户说"老规矩"时：

1. 读取全局规则文件（云同步盘路径，如 `c:\Users\msi\.trae-cn\ai_rules\全局规则.md`）；
2. 读取项目层文件：`现状快照.md`、`变更日志.md`、`悬挂事项.md`；
3. 复述当前任务边界；
4. 汇报"自上次更新以来哪些内容已过时 / 需要补充"；
5. 汇报"变更日志已有 N 条未 review"；
6. 动手前，把将要修改的文件复制到 `history/` 文件夹，文件名加时间戳；
7. **等待用户确认后才开工**。

### 2. 【新】标签仪式

用户切换话题且未带【新】标签时，主动询问：

> "当前任务先挂起？我记录一下现场。"

确认后，把当前任务进度写入 `悬挂事项.md`：任务名、进行到哪、下一步、涉及文件、当时思路。然后再开始新任务。

不带【新】标签的对话，一律视为当前任务的延续。

### 3. 换脑仪式

检测到模型切换或用户明确说"换模型"时：

1. 重新执行开工仪式；
2. 新模型从文件重建状态，不从对话摘要猜测；
3. 如果项目已有"模型分工登记表"，按表分配擅长任务。

### 4. 记入教训仪式

用户纠正模型错误后，用户说"记入教训"或"记入全局教训"时：

1. 将错误模式 → 正确做法提炼为一条；
2. 如果是项目业务相关，写入项目文件；
3. 如果是通用规则，写入全局规则中的"教训清单"；
4. 保持清单最多 10 条，合并同类或淘汰最久未复发的。

### 5. 入库仪式

脚本验收通过后，用户说"入库"时：

1. 将脚本保存到 `scripts/` 文件夹；
2. 在 `工具清单.md` 中登记一行：脚本名、用途、输入输出、格式要点、入库日期；
3. 后续同类任务优先复用，禁止从零重写。

## 四、文件操作规范

1. **文本类文件**（md / txt / csv / json / 代码）的查看、查找替换、编辑，**一律使用内置文件工具，禁止编写 Python 等脚本**。
2. **Office 文件**（docx / xlsx / pptx）允许脚本处理，但需遵守三条纪律：
   - 动手前：一句话说明处理思路和涉及范围；
   - 完成后：必须回读验证，并汇报"改了哪些位置、各改成什么"；
   - 写脚本前：先读 `工具清单.md`，有现成的一律复用或在其基础上修改，**禁止从零重写**。
3. **批量修改前必须列清单**：先列出要改的文件和每处改法，用户确认后再动手。
4. **修改前先备份**：任何文件修改前，复制到 `history/` 并加时间戳命名。

## 五、项目文件结构

每个项目根目录下维护：

| 文件 | 作用 | 更新方式 |
|------|------|----------|
| `现状快照.md` | 当前方案完整有效状态 | 决策变化时整体重写 |
| `变更日志.md` | 只增不改的改动流水账 | 每轮任务结束追加 2-3 行 |
| `悬挂事项.md` | 被打断的未完成任务现场 | 跳转时写入，恢复后删除 |
| `history/` | 任务级时间戳备份 | 动手前自动复制 |
| `工具清单.md` + `scripts/` | 脚本库索引与脚本资产 | 验收后入库 |

## 六、全局规则与项目规则分层

- **全局规则**（`全局规则.md`）：放员工手册、工具偏好、通用教训、模型分工、交付风格。一处维护，处处生效。
- **项目规则**（项目内文件）：放方案状态、变更历史、悬挂事项、项目口径。随项目演进。
- 与项目业务无关的规则，**一律不入项目文件**。

## 七、模型分工登记

如果用户已有 `全局规则.md`中的"模型分工登记表"，按表执行：

- 同一份交付物的"成稿与润色"环节，固定由同一个模型负责，避免风格接缝；
- 数据处理、脚本编写等任务可切换模型，但切换时必须执行换脑仪式。

## 八、交付风格要求

默认遵守用户全局规则中的交付风格。如无特殊说明：

- 语言积极、避免指责性/绝对化表达；
- 标题 30-40 字，段落不超过 40 字；
- Markdown 输出前自检符号闭合、表格单元格无换行、列表无超一层嵌套。

## 九、失败应对

如果用户说"你之前不是这么改的""又错了""还是漏了"：

1. 立即停下当前动作；
2. 读取 `变更日志.md` 和 `history/` 对应备份，定位上次有效状态；
3. 向用户确认：是要恢复旧状态，还是按新理解继续；
4. 把这次错误模式记入教训清单。
