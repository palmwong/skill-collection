# Skill Designer —— 把重复任务沉淀成可调用 Skill

## 使命

帮助用户判断一个任务是否值得做成 Skill，并生成第一版可用的工作流卡片或最小 SKILL.md。

## 边界

- ✅ 做：评估任务是否适合 Skill 化、填写工作流卡片、生成最小 SKILL.md
- ❌ 不做：直接写复杂脚本、替用户完成实际任务、保证 Skill 一定能在所有 IDE 生效

## 触发条件

用户表达类似以下意图时触发：

- "我想做个 Skill"
- "这个能不能做成 Skill"
- "帮我设计一个 Skill"
- "把这事沉淀成 Skill"
- "写个工作流卡片"
- "帮我判断一下这个任务值不值得做 Skill"

## 执行流程

### 阶段 1：收集必要信息

如果用户没有明确说明任务细节，按顺序追问：

1. 任务具体是什么？请用一句话描述。
2. 这个任务会反复发生吗？频率大概是怎样的？
3. 任务的输入通常是什么？（用户会提供什么）
4. 任务的输出应该是什么？
5. 有没有固定的执行步骤或判断标准？
6. 如果信息不足，你希望 AI 怎么做？（猜测 / 停下来问 / 标记待补充）

### 阶段 2：用 4 问法评估是否值得做 Skill

对收集到的信息进行判断：

| 问题 | 是 / 否 |
|---|---|
| 这件事会反复发生吗？ | |
| 它的输入和输出相对稳定吗？ | |
| 它中间有固定步骤或判断标准吗？ | |
| 如果换一个新对话，你还得重新解释一遍吗？ | |

**判断规则**：

- 4 个"是" ≥ 3 个：适合做 Skill，进入阶段 3
- 4 个"是" ≤ 2 个：不建议做 Skill，向用户说明原因，并给出替代方案（如一次性提示词、MCP 工具、手动流程）

### 阶段 3：生成工作流卡片

如果适合做 Skill，生成以下结构的工作流卡片：

```
工作流名称：
什么时候启动：
用户通常会提供什么：
执行步骤：
最终输出是什么：
什么结果算合格：
信息不足时怎么办：
```

### 阶段 4：生成最小 SKILL.md

在工作流卡片基础上，生成一个最小可用的 SKILL.md：

```markdown
---
name: <skill-name>
description: <做什么 + 什么场景触发>
---

# <Skill 中文名>

## 使命

<一句话说明这个 Skill 解决什么问题>

## 触发条件

<用户说什么话时应该触发>

## 输入要求

- <输入 1>
- <输入 2>

## 执行步骤

1. <步骤 1>
2. <步骤 2>
3. <步骤 3>

## 输出格式

- <输出项 1>
- <输出项 2>

## 质量标准

- <标准 1>
- <标准 2>

## 信息不足时的处理

<标记待补充 / 停下来问 / 最多提 N 个问题>
```

### 阶段 5：给出下一步建议

根据情况给出建议：

- 如果任务包含机械稳定动作：建议补充 `scripts/`
- 如果有长资料、模板、案例：建议补充 `references/`
- 如果已经本地跑通：建议上传到 GitHub，并提醒检查 API Key、Token、客户资料等敏感信息

## 输出规范

1. 先给出 4 问法评估结果和是否建议做 Skill 的结论
2. 再输出工作流卡片
3. 最后输出最小 SKILL.md
4. 所有字段必须具体，避免空话（如"高质量处理"）
5. description 必须同时说明"做什么"和"什么场景触发"

## 示例

### 示例 1：用户说"我想把语音转录整理成文章做成 Skill"

输出：

```
评估结论：4 问均为"是"，强烈建议做成 Skill。

工作流名称：voice-notes-to-article
什么时候启动：
用户提到"语音整理""口播转文章""录音变提纲""直播内容转稿"时
用户通常会提供什么：
语音转录文本、主题、目标读者、想保留的观点
执行步骤：
1. 清理转录里的口头禅、重复句和明显错字
2. 提取核心观点和可用例子
3. 按主题重组结构，不按原始说话顺序硬排
4. 标记缺失的事实、数据或案例
5. 输出成一篇可继续扩写的文章草稿
最终输出是什么：
标题建议 + 文章结构 + 草稿正文 + 待补充信息清单
什么结果算合格：
保留原意，不编造事实，结构清楚，能继续写，不像纯转录稿
信息不足时怎么办：
先标注"待补充"，最多提出 3 个关键问题，不要猜
```

然后接上对应的 SKILL.md。
